(`backend/models/disease_model.pkl`, unchanged by this review) and an
**experimental candidate** produced during this review
(`backend/models/experiments/disease_model_v2_candidate.pkl`,
metadata at `disease_model_v2_candidate.metadata.json`). All numbers
below were generated by actually running the code in this repository
against the actual dataset — none are estimated or copied from memory.

**The experimental candidate is not deployed.** `backend/app/config.py`
still points only at `disease_model.pkl`, and `POST /predict` remains
unregistered (returns 404) regardless of anything in this report.

## 2. Experimental candidate — methodology

To evaluate and (if possible) improve on the production configuration
**without** touching it, this review built
`backend/scripts/optimize_random_forest.py`, which:

1. Loads the identical `merged_dataset.csv` (no new data was added — see
   `DATASET_QUALITY_REPORT.md` §3 for why legitimate expansion was not
   possible).
2. Computes a group ID per unique 229-feature vector and splits
   train/test with `StratifiedGroupKFold` keyed on that group, so **no
   exact symptom vector can appear on both sides of the split** (0 rows
   overlap, verified — vs. 1,485 for the production split).
3. Re-evaluates the *production hyperparameters* on this cleaner split
   as an apples-to-apples baseline.
4. Runs `RandomizedSearchCV` (training data only, group-aware CV) to
   search for a better configuration.
5. Evaluates the winning configuration exactly once on the held-out test
   set.
6. Cross-validates the winning hyperparameters (5-fold, group-aware) as
   a robustness check.
7. Saves every metric, the confusion matrix, and the per-class report to
   `backend/reports/`.

**Search budget note (transparency required by this task):** the first
attempt used a 40-candidate × 5-fold sweep (200 fits) with parameters up
to `n_estimators=600`/`max_depth=40`. After running **55+ minutes without
completing** on the development machine, it was stopped and replaced
with a deliberately smaller, bounded search: **15 candidates × 3-fold
CV (45 fits)**, with the parameter ranges capped at values already
confirmed fast (`n_estimators<=400`, `max_depth<=32`). This is a smaller
search than originally planned, not a lower-integrity one — it completed
in 246 seconds, and its result was still cross-validated and evaluated
on a completely untouched test set exactly once.

## 6. Model accuracy target

| | |
|---|---|
| Target | 95%–98% |
| Minimum target | 95% |
| **ACTUAL ACCURACY** | **89.27%** (tuned candidate, leakage-safe, untouched test set) |
| **STATUS** | **TARGET NOT ACHIEVED** |

### Technical reason (computed, not assumed)

This review computed the **theoretical maximum accuracy any classifier
could achieve using only these 229 binary symptom features**, by
grouping all 93,993 rows by their exact feature vector and summing, per
group, the count of the majority label:

```
93,993 total rows
88,894 unique feature-vector groups
Sum of per-group majority-label counts: 88,894
Theoretical ceiling: 88,894 / 93,993 = 94.58%
```

**No model — regardless of algorithm, tuning, or training time — can
exceed 94.58% accuracy on this exact dataset**, because 4,127 distinct
symptom presentations (9,226 rows, 9.8% of the dataset) are shared
identically by two or more different diseases (e.g. *acute bronchitis*
vs. *asthma*, *cholecystitis* vs. *esophagitis*, *appendicitis* vs.
*diverticulitis* — see `leakage_report.json` for the full list). Since
each such group has, by construction, no repeated (vector, label) pair
(exact duplicates were already removed upstream), at most one row per
group can ever be correctly labeled by any function of the input alone —
the rest are mathematically guaranteed misses.

**The tuned model's 89.27% captures 94.4% of this theoretical ceiling**
(89.27 / 94.58). Reaching 95%+ overall accuracy is not achievable with
this feature set — it would require additional discriminating
information not present in binary symptom presence alone (vitals, labs,
exam findings, symptom duration/severity, or patient history), or a
fundamentally different, larger, less-ambiguous dataset.

**Selection: RandomForest (tuned).** It wins on every accuracy-family
metric (accuracy, weighted/macro F1, balanced accuracy, top-3 accuracy),
trains fast, and is the algorithm already integrated throughout this
codebase (`predict.py`, `train.py`, Firestore document ID mapping via
`model.classes_`), so switching would add integration risk for no
accuracy benefit. **HistGradientBoosting's 1.6 MB size is a genuine,
noted advantage** for constrained deployment targets, but its lower
accuracy on every metric disqualifies it here — model size was not the
deciding factor, correctness was, per this task's explicit instruction
not to select based on convenience over generalization/correctness.

No model closed the gap to 95% — confirming §6's finding that the
limitation is the **dataset's inherent label ambiguity**, not the
algorithm choice.

## 9. Confidence analysis (`predict_proba` behavior)

Computed on the tuned model's actual test-set probability outputs
(`backend/models/experiments/disease_model_v2_candidate.pkl`):

| Top-class probability | % of test cases at/above this confidence | Accuracy among those cases |
|---:|---:|---:|
| ≥ 0.80 | 17.1% | 100.00% |
| ≥ 0.70 | 33.0% | 100.00% |
| ≥ 0.60 | 48.6% | 99.95% |
| ≥ 0.50 | 62.3% | 99.42% |
| ≥ 0.40 | 74.9% | 97.72% |
| ≥ 0.30 | 85.9% | 95.11% |

| Top-class probability | % of test cases below this confidence | Accuracy among those cases |
|---:|---:|---:|
| < 0.30 | 14.1% | 53.85% |
| < 0.40 | 25.1% | 64.08% |
| < 0.50 | 37.7% | 72.53% |

Median confidence across all test predictions: 0.590. Mean: 0.570.

### Derived confidence policy (data-driven, not arbitrary)

The data shows a clear, usable split: predictions at **≥0.50 confidence
are correct 99.4%+ of the time** (covering 62% of cases), while
predictions **below 0.30 confidence are correct only ~54% of the time**
(barely better than chance across 100 classes) and should not be
presented as reliable.

**Recommended policy** (evaluation-only — not wired into any active
route, since `/predict` remains disabled):

- **≥ 0.50** — high confidence: safe to surface as a ranked decision-
  support suggestion.
- **0.30 – 0.50** — moderate confidence: surface with an explicit
  uncertainty indicator; recommend clinical review.
- **< 0.30** — low confidence: do not present as a suggestion; route to
  "needs clinical review" instead (mirroring the pattern
  `health_category_service.py` already uses for its own rule-based
  ambiguity handling).

This policy is a **recommendation derived from this evaluation**, for if
and when the Random Forest is ever reconsidered for production use. It
changes nothing about the current system: **confidence must never be
presented as medical certainty**, and no code path currently surfaces
this model's predictions to any user.

## 11. Known limitations (this evaluation, specifically)

- 89.27% accuracy is below the 95% target; §6 shows this is bounded by
  an inherent 94.58% ceiling in the dataset itself, not primarily an
  algorithm/tuning deficiency.
- The hyperparameter search was intentionally bounded (15 candidates ×
  3-fold, capped parameter ranges) after a larger search proved
  infeasible in this environment — a wider search might find a
  marginally better configuration, but cannot exceed the 94.58% ceiling.
- Several classes (COPD, skin polyp, skin pigmentation disorder, acute
  bronchospasm) have recall below 70% and would need additional
  distinguishing features, not just tuning, to improve meaningfully.
- This evaluation, like the production model's, is not a clinical
  validation — see `AI_ALGORITHM_QA.md` §12 for that distinction.
- The experimental model file itself is not stored in git (111.3 MB,
  exceeds GitHub's 100 MB limit) — only its checksum, hyperparameters,
  and a deterministic reproduction command are versioned.
- This model remains **experimental and disconnected from production**.
  No route, config default, or Flutter client code was changed to use it.
