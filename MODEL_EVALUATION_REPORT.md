## 2a. This session's changes (2026-08-11): preprocessing fix, re-tuning, hierarchical test

Three legitimate improvement avenues were investigated, per the task's
explicit request to keep pushing past 89.31% rather than stop at the first
negative result:

1. **Preprocessing fix (adopted).** The raw source file contains two columns
   for the same symptom, `regurgitation` and `regurgitation.1` (a literal
   duplicate in the source CSV's own header, not a loading artifact — see
   `DATASET_QUALITY_REPORT.md` §1.1a). Adding
   `"regurgitation.1": "regurgitation"` to
   `backend/dataset/mappings/symptom_mapping.json` lets the pipeline's
   existing logical-OR column-merge collapse them, reducing 229→228
   features. Retrained with **identical hyperparameters** on the corrected
   dataset: **89.3138% → 89.3399%** Top-1 (+0.026 points), Top-3
   98.3936%→98.5052% (+0.11 points), same leakage-safe split methodology.
   Small but real and honestly measured — not the primary lever on the 89%
   plateau, but a legitimate correctness fix, kept as `disease_model_v4`.

2. **Further hyperparameter search (not adopted — confirms current config
   is already near-optimal).** A bounded `RandomizedSearchCV` (15
   candidates × 3-fold `StratifiedGroupKFold`, same search space as the
   original tuning run: `n_estimators`, `max_depth`, `min_samples_leaf`,
   `min_samples_split`, `max_features`, `criterion`, `class_weight`) was
   re-run on the corrected 228-feature dataset
   (`backend/scripts/optimize_random_forest.py`,
   `backend/reports/rf_search_results.json`,
   `backend/reports/rf_optimization_final_report.json`). Its CV-selected
   "best" candidate (`min_samples_leaf=1`, everything else unchanged)
   scored **89.13%** on the real held-out test set — *below* the existing
   production config's 89.34%. Per this task's rule to select on
   validation/CV, not by repeatedly peeking at the test set, this
   CV-selected candidate is correctly **not adopted**; the already-tuned
   production hyperparameters remain the best found configuration.

3. **Hierarchical (category → disease) classification (tested,
   rejected).** See `DATASET_QUALITY_REPORT.md` §11 for the full
   methodology. Summary: a stage-1 category classifier reached 98.69%
   accuracy on the project's existing 12-category taxonomy, but the full
   two-stage pipeline's disease-level accuracy (88.96%) was *below* the
   flat model (89.34%) because stage-1 errors compound into stage-2. Not
   adopted.

**Model comparison (RF vs. ExtraTrees vs. HistGradientBoosting) was not
re-run this session.** The prior comparison (§7) showed RF winning by a
clear, substantial margin (89.31% vs. 88.96% vs. 87.63% — a 0.35–1.68 point
gap) on the 229-feature dataset. The dataset change this session removed
exactly one redundant, noisy column and moved RF's own accuracy by +0.03
points; a change of that size has no realistic path to overturn a
multi-point gap between algorithms. Re-running the full three-way
comparison was judged not to be a good use of the remaining evaluation
window given this near-zero expected information gain — recorded here
transparently as a deliberate scope decision, not an oversight.

## 2. Tuning and evaluation methodology

The tuning experiment that selected the current configuration built
`backend/scripts/optimize_random_forest.py`, which:

1. Loads the identical `merged_dataset.csv` (no new data was added — see
   `DATASET_QUALITY_REPORT.md` §3 for why legitimate expansion was not
   possible).
2. Computes a group ID per unique 229-feature vector and splits
   train/test with `StratifiedGroupKFold` keyed on that group, so **no
   exact symptom vector can appear on both sides of the split** (0 rows
   overlap, verified — vs. 1,485 for the production split).
3. Re-evaluates the historical *production hyperparameters* on this cleaner split
   as an apples-to-apples baseline.
4. Runs `RandomizedSearchCV` (training data only, group-aware CV) to
   search for a better configuration.
5. Evaluates the winning configuration exactly once on the held-out test
   set.
6. Cross-validates the winning hyperparameters (5-fold, group-aware) as
   a robustness check.
7. Saves every metric, the confusion matrix, and the per-class report to
   `backend/reports/`.

**Search budget note (transparency required by this task):** the first
attempt used a 40-candidate × 5-fold sweep (200 fits) with parameters up
to `n_estimators=600`/`max_depth=40`. After running **55+ minutes without
completing** on the development machine, it was stopped and replaced
with a deliberately smaller, bounded search: **15 candidates × 3-fold
CV (45 fits)**, with the parameter ranges capped at values already
confirmed fast (`n_estimators<=400`, `max_depth<=32`). This is a smaller
search than originally planned, not a lower-integrity one — it completed
in 246 seconds, and its result was still cross-validated and evaluated
on a completely untouched test set exactly once.

After that search, a targeted eight-candidate RF search scored **accuracy**
instead of only weighted F1, using the same three-fold group-safe CV on the
training partition. It selected `min_samples_leaf=2`; the selected candidate
was then evaluated once on the locked test partition and became version
`disease_model_v3`. The prior version `disease_model_v2` remains recorded in
the model registry and its 89.2713% result is retained as the direct baseline.

## 6. Model accuracy target

| | |
|---|---|
| Target | 95%–98% |
| Minimum target | 95% |
| **ACTUAL ACCURACY** | **89.34%** (v4, leakage-safe, locked test set) |
| **STATUS** | **TARGET NOT ACHIEVED** |

### Technical reason (computed, not assumed)

This review computed the **theoretical maximum accuracy any classifier
could achieve using only these 228 binary symptom features**, by
grouping all 93,993 rows by their exact feature vector and summing, per
group, the count of the majority label:

```
93,993 total rows
88,878 unique feature-vector groups
Sum of per-group majority-label counts: 88,878
Theoretical ceiling: 88,878 / 93,993 = 94.56%
```

**No model — regardless of algorithm, tuning, or training time — can
exceed 94.56% accuracy on this exact dataset**, because 4,140 distinct
symptom presentations (9,255 rows, 9.8% of the dataset) are shared
identically by two or more different diseases (e.g. *acute bronchitis*
vs. *asthma*, *cholecystitis* vs. *esophagitis*, *appendicitis* vs.
*diverticulitis* — see `leakage_report.json` for the full list). Since
each such group has, by construction, no repeated (vector, label) pair
(exact duplicates were already removed upstream), at most one row per
group can ever be correctly labeled by any function of the input alone —
the rest are mathematically guaranteed misses.

**The v4 model's 89.34% captures 94.5% of this theoretical ceiling**
(89.34 / 94.56). Reaching 95%+ overall accuracy is not achievable with
this feature set — it would require additional discriminating
information not present in binary symptom presence alone (vitals, labs,
exam findings, symptom duration/severity, or patient history), or a
fundamentally different, larger, less-ambiguous dataset. This session
re-confirmed (§2a) that neither further RF tuning nor a hierarchical
category-first approach can close this gap — the limitation is the
dataset's inherent label ambiguity, not an algorithm or architecture
choice.

### Derived confidence policy (data-driven, not arbitrary)

The data shows a clear, usable split: predictions at **≥0.50 confidence
are correct 99.6%+ of the time** (covering 58% of cases), while
predictions **below 0.30 confidence are correct only ~55% of the time**
(barely better than chance across 100 classes) and should not be
presented as reliable.

**Recommended policy** (evaluation-only — not wired into any active
route, since `/predict` remains disabled):

- **≥ 0.50** — high confidence: safe to surface as a ranked decision-
  support suggestion.
- **0.30 – 0.50** — moderate confidence: surface with an explicit
  uncertainty indicator; recommend clinical review.
- **< 0.30** — low confidence: do not present as a suggestion; route to
  "needs clinical review" instead (mirroring the pattern
  `health_category_service.py` already uses for its own rule-based
  ambiguity handling).

This policy is a **recommendation derived from this evaluation**, for if
and when the Random Forest is ever reconsidered for production use. It
changes nothing about the current system: **confidence must never be
presented as medical certainty**, and no code path currently surfaces
this model's predictions to any user.

## 11. Known limitations (this evaluation, specifically)

- 89.34% accuracy is below the 95% target; §6 shows this is bounded by
  an inherent 94.56% ceiling in the dataset itself, not primarily an
  algorithm/tuning deficiency. This session re-confirmed the ceiling is
  not closeable by further RF tuning (§2a.2) or a hierarchical
  category-first architecture (§2a.3).
- The hyperparameter search was intentionally bounded (15 candidates ×
  3-fold, capped parameter ranges) both in the original tuning run and in
  this session's re-run on the corrected dataset — a wider search might
  find a marginally better configuration, but cannot exceed the 94.56%
  ceiling.
- Several classes (skin polyp, COPD, skin pigmentation disorder,
  personality disorder) have recall below 70% and would need additional
  distinguishing features, not just tuning, to improve meaningfully.
- This evaluation, like the production model's, is not a clinical
  validation — see `AI_ALGORITHM_QA.md` §12 for that distinction.
- The experimental model file itself is not stored in git (111.3 MB,
  exceeds GitHub's 100 MB limit) — only its checksum, hyperparameters,
  and a deterministic reproduction command are versioned.
- This model remains **experimental and disconnected from production**.
  No route, config default, or Flutter client code was changed to use it.
- **This session also found and fixed a real bug in the separate, active
  on-device AI classifier** (Model 2, `HealthAIClassifier` — the system
  BHWs actually use today), unrelated to this Random Forest: its ML path
  has no input feature for structured prenatal fields
  (gravida/para/gestationalAge/riskLevel) and was observed to
  misclassify a high-risk preeclampsia-pattern case as "Communicable
  Disease." Fixed by routing records with those fields to the rule-based
  path, which does read them; verified with new tests in
  `test/app/health_ai_classifier_test.dart`. Other, lower-stakes
  miscalibrations in that same ML model were also observed (e.g., a
  plain adult communicable-disease case classified as "Pediatric Care")
  and are **not** fixed — they stem from that model being trained only on
  synthetic data (`train_model/train_health_classifier.py:create_synthetic_training_data`),
  which the project's own `train_model/README.md` already states is not
  acceptable as production evidence. Retraining it would require real
  Firebase-exported labeled records (not available in this environment)
  or installing TensorFlow to produce another synthetic-only model,
  which would not be a legitimate fix per that stated policy. See
  `docs/AI_ACCURACY_GAP_ANALYSIS.md` for the full account.
